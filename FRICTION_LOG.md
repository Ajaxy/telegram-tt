# Friction log

Open problems in code patterns, contributor practices, and tooling that contributors encounter but cannot reasonably resolve within their current task. This is a shared list for follow-up work when someone has time. Entries describe the problem and its impact; estimates and proposed fixes are not required, and resolution preferences or suggestions are welcome.

Before adding an entry or picking one up, follow the [friction log guidance in AGENTS.md](AGENTS.md#friction-log). Extend matching entries, recheck the current code before starting work, and remove resolved problems or update what remains.

## Tracking active requests inside actions

Async actions have no shared mechanism for checking whether their invocation is still current after an `await`. [TeactN](src/lib/teact/teactn.tsx) exposes completion promises through `getPromiseActions`, but overlapping calls still need feature-specific bookkeeping to prevent older results from overwriting newer state. [AI composition](src/global/actions/api/ai.ts) increments a counter, stores the request ID on the editor tab, and compares it after the API call. [Wallet actions](src/global/actions/api/wallet.ts) repeat this with counters and per-tab maps for state, limits, quotes, fees, and mnemonic loading. Free messages links add two more: `applyNoPaidMessagesToken` in [chat actions](src/global/actions/api/chats.ts) keeps a module-level set of in-flight imports, and the [QR code hook](src/components/modals/qrCode/hooks/useFreeMessagesCode.ts) keeps a generation counter to drop stale export replies. Contributors must maintain these guards alongside checks that the original UI context is still active.

The [worker connector](src/api/gramjs/worker/connector.ts) tracks transport requests internally, and [API invocation](src/api/gramjs/methods/client.ts) supports chat/thread and call-group cancellation. These mechanisms do not expose general active-request ownership to global action handlers, so request IDs and stale-response checks remain scattered across features.

## Reverting optimistic global updates

Optimistic actions manually save original values, publish local changes, call the API, and restore the affected paths when the request fails. In [chat actions](src/global/actions/api/chats.ts), `toggleJoinRequest` saves and restores both the chat's join-request flag and its full-info guard bot, while `setMainProfileTab` separately preserves the old tab. In [settings actions](src/global/actions/api/settings.ts), `sortChatUsernames` keeps a copy of the original usernames and restores it if reordering fails.

There is no shared rollback helper for these edits. Each action must keep its saved values and restoration paths aligned as the optimistic update evolves, including changes across multiple branches of global state. Failure can arrive after another invocation or unrelated state changes, so restoring an entire earlier global snapshot would discard intervening updates. Any shared support needs to preserve those updates and account for overlapping changes to the same fields.

## Rich notification content across the serialization boundary

[`showNotification`](src/global/actions/ui/initial.ts) stores notification payloads in tab global state, which is synchronized through [`BroadcastChannel`](src/util/browser/multitab.ts). [`ApiNotification`](src/api/types/misc.ts) accepts strings or localization parameter objects, message entities, predefined icons, and action descriptors. Advanced localization variables and the `specialReplacement` option accept `TeactNode` values. Component-valued nodes contain function references, so a notification with a custom inline component can cause `BroadcastChannel.postMessage` to fail during state synchronization. The [renderer](src/components/ui/Notification.tsx) passes localized messages to `lang.with`, so it can consume these values locally. The remaining design question is how to request richer interactive content without placing non-serializable UI values in shared state.

Contributors wanting special elements must work within these representations or extend UI rendering separately. The preference is to keep richer content straightforward to request from actions without introducing a general component-description protocol or converting action files to TSX. The appropriate boundary between serializable notification data and UI composition remains an open design question.

## Separating app and local-tooling lint environments

[`tsconfig.json`](tsconfig.json) covers app source and excludes tests and selected GramJS generators, while [`tsconfig.script.json`](tsconfig.script.json) covers tests, development scripts, plugins, and configuration files. However, [`eslint.config.js`](eslint.config.js) applies the same broad Teact rules and both TypeScript projects to JavaScript and TypeScript files across the repository. The script config also inherits DOM/Web Worker libraries and bundler module resolution from [`tsconfig.base.json`](tsconfig.base.json). The split therefore does not clearly separate the rules and environment assumptions for browser code from tooling running locally in Node.

[`check:ts`](package.json) runs `tsc` against the app config, then repository-wide ESLint; it does not explicitly type-check the script project with a separate `tsc` invocation. This makes the compiler and lint coverage harder to reason about and maintain. With lockfile dependencies installed, the compiler succeeds on Windows, but a repository-wide ESLint run exceeds 4 GB of working memory after more than six minutes and is stopped without results; linting the changed audio/video files separately succeeds. On macOS with Node 26.12.1, the same full ESLint run aborts the process (`Abort trap: 6`) after `tsc` passes, while linting the changed files separately succeeds. In a fresh worktree without `.cache/.eslintcache` it fails with a JavaScript heap out-of-memory error after about 90 seconds. The source of this full-run memory cost is not profiled. The preference is a clear app configuration and a separate local tests/helpers configuration, retaining browser types where tests need them: [Vitest](vitest.config.ts) runs in Node with a jsdom environment, and tests import app code. Shared settings still need to stay consistent without blurring those boundaries.

## Concurrent icon font builds can leave a partial font

[`vite.config.ts`](vite.config.ts) reruns [`buildIcons.ts`](dev/buildIcons.ts) when `src/assets/font-icons` changes, and `npm run icons:build` uses the same `.cache/icons-build` directory. Verified on macOS, 2026-10-26: running the script by hand while the development server rebuilt after an SVG change failed with `ENOTEMPTY: directory not empty, rmdir '.cache/icons-build/input'`. It left `src/styles/icons.woff2` with 325 of 434 glyphs. `icons.css` was complete, so 109 icons (`delete`, `copy`, `close`, `clock`…) rendered empty across the app. The font URL hash is computed from the source SVGs, not from the generated font, so a clean rebuild keeps the same `icons.woff2?<hash>` URL. Open tabs kept the broken font until a cache-bypassing reload. Nothing in the build compares the font's glyph count with the CSS, so a partial font is easy to miss.

## Generated icon files change line endings on Windows

After updating icon sources on Windows, generated [`icons.scss`](src/styles/icons.scss) and [`preview.html`](src/styles/icons/preview.html) can contain CRLF despite their LF attributes in [`.gitattributes`](.gitattributes). This produces modified-file status and Git line-ending warnings even when their normalized content hashes match `HEAD` and `git diff` contains no content changes. [`vite.config.ts`](vite.config.ts) reruns [`buildIcons.ts`](dev/buildIcons.ts) when `src/assets/font-icons` changes, so merging upstream icon updates with the development server running can trigger this noise. The generator does not explicitly normalize these template outputs to LF; the exact source of CRLF emission still needs investigation.

## Matching reaction notifications across delivery sources

Local notifications in [`notifications.tsx`](src/util/notifications.tsx) and server push notifications reach [`pushNotification.ts`](src/serviceWorker/pushNotification.ts) with message IDs and display text, but no shared reaction event ID. Reaction deduplication therefore includes the title and body to distinguish reactions to the same message. Code inspection shows that differently formatted or localized text can produce different identities for the same reaction when delivery moves between local and server sources. The normal client-claim path suppresses server notifications handled by an active client; duplicate delivery during a source transition remains a possibility, not a reproduced browser symptom.

Investigate client-only improvements using the existing server payloads. `notifyAboutMessage` already has `activeReaction.peerId` and the emoji or custom-emoji document ID; carrying these through `PushNotification` preserves a stable local identity independently of rendered text. Inspect existing reaction push payloads for matching fields before attempting to derive the same identity on that path; their availability is not verified here. Another option is to extend the existing client/worker claim exchange with delivery acknowledgements and recent-delivery receipts, so a reconnecting client can check notifications already shown by the worker before displaying delayed reactions. Any handoff matching must preserve distinct reactions to the same message; ambiguous payloads can retain the content-based fallback. These options require only client changes, with no dependency on new server fields or server-generated event IDs.
